# frplus

版: **1.0.0** (2026-11-20)。ライセンス: GNU GPL v3 (`LICENSE`)。同梱の Freerouting は GPL v3 (`NOTICE.txt`)。

本文中の 7 桁の英数字 (01c6432 など) は、開発に使った非公開リポジトリのコミット番号で、このリポジトリには無い。

Freerouting を外側から補うツール。KiCad の基板を Freerouting に渡す前に入力を整え、
結果を KiCad の DRC で検証してから基板に反映する。Freerouting 本体は改造しない。

## インストール (KiCad だけが入っている Windows)

配布用の zip (`python make_package.py` で `dist/` にできる) を展開し、`install.bat` をダブルクリックする。
管理者権限は要らない。次のことをする。

- ツール本体と Freerouting の jar を `%LOCALAPPDATA%\frplus` にコピーする
- Java 25 以降が無ければ、Eclipse Temurin の JRE を取得して `frplus\jre` に展開する (約 60 MB、PATH は変えない)
- KiCad のツールバーにボタンを足す (KiCad を起動し直すと出る)

Python は KiCad 付属のものを使うので、別に入れる必要は無い。コマンドから使うときは
`"C:\Program Files\KiCad\9.0\bin\python.exe" -m frplus ...` とする。
`-m frplus doctor` で KiCad、Freerouting、Java が見つかるかを確かめられる。
消すときは `install.bat -Uninstall` (ボタンと `%LOCALAPPDATA%\frplus` を消す)。

## 必要なもの (自分で揃える場合)

- KiCad 9 (付属の python と kicad-cli を使う)
- Java 25 以降と Freerouting の jar。`freerouting/dev/*.jar` (開発版のビルド) があればそれを、無ければ
  `freerouting/freerouting-*.jar` (リリース版 v2.5.0) を使う。設定の `freerouting_jar` でも指定できる
- 開発版のビルド: Freerouting の master を取得し (検証したのは 2026-11-13 の 01db81c)、Java 26 しか無ければ
  `build.gradle` の toolchain を 26 に変えて `./gradlew.bat executableJar --no-daemon`。できた jar を
  `freerouting/dev/` に置く。完走率と仕上がりはリリース版よりかなり良い (下の表)
- Python 3.12 (標準ライブラリのみ)

## 使い方

```bash
python -m frplus check path/to/board.kicad_pcb
```

事前診断だけ行う (数秒)。出口を塞がれたパッドがあれば、塞いでいるものと対処を表示する。

```bash
python -m frplus route path/to/board.kicad_pcb
```

配線する。既定では元の基板に触らず、`<基板名>_frplus/` に作業用コピーと結果を作る。

```bash
python -m frplus apply path/to/board_frplus
```

結果を確認したあと、検証を通っている場合だけ元の基板を上書きする (同じフォルダに日時付きの
`.bak` を残す)。`route --apply` で配線と反映を続けて行うこともできる。

終了コード: 0 = 検証を通った、1 = 未接続・新しい DRC エラー・出口の無いパッドがある、2 = 実行できなかった。

### KiCad のボタンから使う

```bash
python -m frplus install-plugin
```

KiCad のプラグインフォルダに読み込み用のファイルを 1 つ書く。基板エディターで
「ツール → 外部プラグイン → プラグインを更新」を実行するとツールバーにボタンが出る。
ボタンは保存済みの基板ファイルに対して `route` を実行し、検証を通れば「基板に反映」を押せる。
反映後は「ファイル → 元に戻す」で読み込み直す。

## 何をするか

Freerouting が知らないこと・間違えることを、前後で補う。正否の判定は Freerouting の数字ではなく
KiCad の DRC で行う。

前処理 (Freerouting に渡す前)

1. 基板と `.kicad_pro` / `.kicad_dru` を作業フォルダにコピーする。元の基板には反映まで触らない。
2. ロック済みの配線を固定配線として DSN に書き出す。
3. ネットクラスの線幅・クリアランス・ビア径が基板の最小値を下回っていれば、最小値まで引き上げる。
4. 穴クリアランスを守らせるため、DSN の中だけビア外径を広げる (取り込み時に実寸へ戻す)。
   パッド径が穴径より少し大きい NPTH (キースイッチの位置決め穴など) も、KiCad が銅のあるピンとして DSN に出すので、
   DSN の中だけ「穴径 + 2 x (穴クリアランス - 銅箔クリアランス)」まで広げる。
   部品やパッドに個別に設定したクリアランス (KiCad の DSN 出力が落とすもの) も DSN に書き込む。
   内層の銅を持たないスルーホールのパッドは、DSN に表と裏の形しか出ないので、内層にも穴の分の形を足す
   (足さないと Freerouting が内層で穴を横切る線を引き、KiCad でショートになる)。
5. 内層にベタを持つネットの表面実装パッドのうち、まだ何もつながっていないものにビアを足す。
6. 配線もビアも禁止していないルールエリア (配置用エリアなど) を、配線禁止領域から外す。
   参照名が重複する部品 (ロゴの `G***` が複数あるなど) は、DSN と SES の取り込みの間だけ別名にする
   (KiCad の DSN 出力は参照名が重複すると失敗する)。基板の参照名は変えない。
7. パッド以外のレジスト開口、銅箔層の文字・図形、基板内側のくり抜きの周囲を配線禁止にする。
   パッドの上に図形で描かれたレジスト開口 (パッドが F.Mask を持たない部品) は、パッドのための開口として除く。
8. 出口の無いパッドを探す。ロック済みの配線やビアに囲まれていれば、塞いでいるものを表示して止まる。
9. パッドの内側で止まっている配線の端点を、パッド中心まで延ばす (DSN の中だけ)。

配線

10. 設定を変えた複数の案を並列に Freerouting で配線し、それぞれ取り込んで DRC で採点する。
11. 未接続が残れば、最良の案を引き継いでもう一度配線する (前回の配線は引き剥がしてよいものとして渡す)。ベタ経由でつながるはずだったのに
    切れているネットは、次回は通常のネットとして引き直させる。改善が止まったらやめる。

仕上げ (案ごとに実行)

12. Freerouting が絞った線 (ネットクラスの 75% や 50% の幅) をネットクラスの線幅に戻す。
    戻すとクリアランス違反になる線は細いまま残して報告する。
13. 配線で分断されたベタの島を、同じネットの島が重なる場所にビアを打ってつなぐ。
14. 宙ぶらりんの線とビア (ロックされていないもの) を消す。
15. DRC を実行し、未接続と「配線前より増えたエラー」を報告する。ロック済みの配線の先が未接続のまま残った
    ネットは、`release_nets` に入れれば引き直せると案内する (ロックはユーザーの意図なので勝手には外さない)。

## 設定

基板の隣に `<基板名>.frplus.json` を置く (または `--config` で指定)。すべて省略できる。

| 項目 | 既定 | 意味 |
|---|---|---|
| `release_nets` | `[]` | ロック済み配線を外して引き直させるネット。書いたものだけ外す |
| `plane_layers` | `[]` | ベタ専用にする層。信号を引かせない |
| `plane_fanout` | `true` | 内層ベタのネットのパッドにビアを足す |
| `on_trapped` | `"stop"` | 出口の無いパッドがあるとき。`"warn"` なら報告して配線を続ける |
| `unroute` | `false` | ロックされていない既存配線を消してから配線する |
| `variants` | `"auto"` | 並列に試す設定案。`auto` は 1 回目が `default` `nofanout` `noneck` `plain`、開発版のやり直しの回はコスト違いの `cheapvia` `cheapvia_dir` `ripup_low` `nofan_cheapvia` を足して 8 案 |
| `max_resume` | `3` | 未接続が残ったときに配線をやり直す最大回数 |
| `local_ripup_mm` | `3.0` | 全体の引き剥がしで改善しないとき、未接続の箇所からこの距離までの配線だけ引き剥がせる形でもう一度配線する |
| `resume_ripup` | `true` | やり直しのとき、前回の配線を引き剥がして引き直すことを許す。`false` なら前回の配線を固定して残りだけ引かせる |
| `max_passes` | `100` | Freerouting 1 回あたりの配線パス数の上限 (`route --max-passes N` でも指定できる)。改善が 10 パス止まれば、その前に Freerouting 自身が止めるので、行き詰まった基板は早く終わり、改善が続く基板は回り続ける |
| `timeout_sec` | `3600` | 止まらなくなったときの保険の時間上限 (秒)。時間切れでもそこまでの結果は使う。`null` で無制限 |
| `reroute_broken_pours` | `true` | ベタ経由でつながらなかったネットを通常のネットとして引き直す |
| `stitch_pours` | `true` | 分断されたベタの島をビアでつなぐ |
| `mask_keepouts` | `true` | レジスト開口や銅箔層の文字・図形の上に配線させない |
| `accept_errors` | `[]` | 配線で増えても反映を止めない DRC エラー種別 |
| `thermal_retry` | `4` | 完走したのに残ったエラーが熱逃げ (`starved_thermal`) だけのとき、最良の結果を作った回と同じ入力を、別の設定の案でこの本数まで配線し直す (良くなればそれを最適化する)。`0` でしない |
| `max_parallel` | `null` | 同時に動かす Freerouting の本数の上限。`null` は搭載メモリから決める (1 本 2 GB として、メモリの約 7 割まで)。入りきらない案は順番待ちになる |
| `via_in_pad` | `"auto"` | 同じネットのパッドの中にビアを打たせる。`auto` は元の配線がそうしていれば許可 (開発版のみ) |
| `via_touching_pad` | `"auto"` | 同じネットのパッドのすぐ隣にビアを打たせる。`auto` は同上 (開発版のみ) |
| `optimize` | `"complete"` | Freerouting の最適化段。`complete` は未接続が無くなってから 1 回だけ走らせる (配線中は止める)。`always` は毎回、`never` は使わない |
| `preset` | `null` | 基板メーカーの製造能力に合わせた下限。`jlcpcb-2layer` `jlcpcb-4layer` `jlcpcb-6layer` (下の「プリセット」) |
| `extra_args` | `[]` | Freerouting にそのまま渡す追加の引数 (実験用) |
| `freerouting_jar` | 自動 | jar の場所 |
| `java` | 自動 | java.exe の場所。省略時は同梱の `jre`、無ければ PATH の java (25 以降) |
| `kicad_bin` | 自動 | KiCad の bin フォルダ |

上限は時間ではなく回数で決める。時間で縛ると、速いマシンほど多くのパスを回せて結果が変わるため。
所要時間は基板とマシン次第で、OpenDrone (8 層、910 パッド) は 1 パス 1〜3 分かかる。並列に回すと 1 本あたりは
遅くなる (4 本で 1.7 倍) が、合わせた処理量は 2.3 倍になる。

## プリセット

設定の `"preset"` で、基板メーカーの追加料金なしの製造能力を下限として使う。基板の設計ルールやネットクラスが
これより緩いときだけ、配線中はこの値まで引き上げる (ビア径は結果の基板でも広げる)。ユーザーの設定より厳しい値を
緩めることはせず、元の基板の設計ルールも書き換えない。

| プリセット | 最小線幅 / 間隔 | ビア (穴 / 外径) | 穴と線 | 基板端 | パッド内ビア |
|---|---|---|---|---|---|
| `jlcpcb-2layer` | 0.10 / 0.10 mm | 0.20 / 0.45 mm 以上 | 0.20 mm | 0.20 mm | 打たせない |
| `jlcpcb-4layer` | 0.09 / 0.09 mm | 0.20 / 0.45 mm 以上 | 0.20 mm | 0.20 mm | 打たせない |
| `jlcpcb-6layer` | 0.09 / 0.09 mm | 0.20 / 0.45 mm 以上 | 0.20 mm | 0.20 mm | `via_in_pad` の設定どおり (樹脂充填が既定の工程) |

- 値は JLCPCB の [PCB Capabilities](https://jlcpcb.com/capabilities/pcb-capabilities) (2026-11-17 に確認) の標準の最小値。
  銅箔は外層 1 oz、内層 0.5 oz (同社の既定) を想定している。2 oz にするなら、ネットクラスを自分で広げること
  (2 層 0.16 mm、多層 0.15 mm)
- ページで追加料金の条件が書かれているのはビアだけ (穴 0.1 / 0.15 mm、または穴 0.2 / 0.25 mm でビア外径 0.45 mm 未満は割高)。
  線幅などは追加料金の記載が無いので標準の最小値をそのまま使った。ネットクラスのビアの穴がこれより小さいときは
  注意を出す (穴径は DSN の中では変えられない)
- 基板端は外形をルーターで加工する場合の値。V カットなら 0.4 mm なので、基板の設定で広げること
- 基板の層数とプリセットの層数が違えば注意を出す
- 作者の 4 層基板 (非公開、事前配線なし) は `jlcpcb-4layer` で 77 秒で完走、新規エラー 0

## 構成

- `frplus/kicad_side.py` — 基板の読み書き。KiCad 付属 python で動く。pcbnew に触るのはここだけ
- `frplus/dsn.py` — DSN の前処理、SES の結果を DSN へ書き戻す処理、ルールの読み取り
- `frplus/geom.py` — 出口の無いパッドの検出、内層ベタへのビア配置
- `frplus/kicad_plugin.py` — KiCad のツールバーボタン
- `frplus/tools.py` — KiCad、kicad-cli、Freerouting の呼び出しとログ解析
- `frplus/route.py` — 全体の流れ

## 知っておくこと

- 線幅はネットクラスどおりになる。電源を太くしたいなら、KiCad 側でネットクラスを設定しておくこと。
  ネットクラスが 1 つしか無い基板では、電源も信号と同じ幅で引かれる。
- KiCad の SES 取り込みは、部品を SES 記載の位置へ動かす。DSN を出した基板と取り込む基板は
  同じものにすること (このツールは同じ作業用コピーを使う)。
- Freerouting v2.5.0 は存在しない設定名を警告だけで無視する。このツールはそれをエラーにする。
- Freerouting の利用統計送信は常に無効にして起動する。
- Freerouting は、ビアと「同じネットの」パッド・ビアの間にもクリアランスを要求する。KiCad では
  違反にならない配置でも、Freerouting はそこにビアを打たない。手で置いたビアがこれに当たると
  「pre-existing clearance violation」と警告される。このツールの診断とビア配置はこの規則に合わせてある。
  開発版ではこの制限を外せる (`via_in_pad` `via_touching_pad`)。開発版は基板に残っているビアを見て自動で
  決めるが、配線を消してから渡すと判定材料が無くなるので、このツールが消す前に数えて明示的に渡す。
  配線の無い新しい基板では `auto` は禁止になるので、パッド内ビアを使う設計なら `true` を指定すること。
- Freerouting は決定的で乱数を持たない。同じ入力からは同じ結果しか出ないので、設定を変えた案を並べている。
- 出口の判定は、基板外形を外接矩形で見て、キープアウト領域は見ない。複雑な外形では診断がずれることがある。
- 配線禁止にする領域 (レジスト開口、銅箔層の文字、くり抜き) は外接矩形で近似している。くり抜きは KiCad の外形ポリゴンの穴だけを使う。
- KiCad のボタンは KiCad 9.0.9 の画面上で動作を確認してある。
- `frstage.py` と `baseline/` `staged*/` `ablate/` `fix/` `mop/` は調査時の実験で、ツール本体ではない。
- `tests/compare.py` は人手配線と自動配線の配線長・ビア数・線幅を比べる。`tests/near.py` は未接続箇所の周辺を列挙する。

## 試した基板

配線をすべて消してから自動配線した結果 (2026-11-15、`bash tests/bench_all.sh`)。開発版は master の 01db81c を自分でビルドしたもの。

| 基板 | 規模 | v2.5.0 | 開発版 |
|---|---|---|---|
| 作者の 4 層基板 (非公開、事前配線なし) | 4 層、277 パッド | 未接続 0、新規エラー 0 | 未接続 0、新規エラー 0 |
| pic_programmer (KiCad 同梱) | 2 層、247 パッド | 未接続 0、新規エラー 0 | 未接続 0、新規エラー 0 |
| multichannel_mixer (KiCad 同梱) | 2 層、327 パッド | 未接続 0、サーマル接続のエラー 1 | 同じ |
| StickHub (KiCad 同梱) | 2 層、16x40 mm に 278 パッド、45 度配置の QFN | 未接続 9、線幅エラー 4 | 未接続 1〜4、新規エラー 0 |
| OpenDrone AIO FC F405 | 8 層、34x34 mm に 910 パッド | 未接続 80、エラー 14 | 未接続 45〜51、クリアランスエラー 9 |

上の表は、パッドの中や隣へのビアを禁止したままの結果。元の配線がそうしたビアを使っている基板では、
許可すると大きく変わる (2026-11-15、開発版):

| 基板 | 元の配線のビア | 禁止 | 隣だけ許可 | 中も許可 |
|---|---|---|---|---|
| StickHub | 87 個中、隣 19 個、中 0 個 | 未接続 1〜4 | 未接続 3 | 未接続 0、新規エラー 0 |
| OpenDrone | 609 個中、中 239 個、隣など 181 個 | 未接続 45〜51、エラー 9 | — | 未接続 20、クリアランスエラー 16 |

`auto` は元の配線がやっている範囲までしか許可しないので、StickHub は「隣だけ」になる。

### やり直しの回の改良 (2026-11-15、開発版、`auto` のまま)

| 版 | 変更 | StickHub | OpenDrone |
|---|---|---|---|
| 前回の配線を固定 | — | 未接続 1 | 未接続 20、クリアランスエラー 16、71 分 |
| v4 | 下の 5 点すべて | 未接続 0、新規エラー 0、10 分 | 未接続 1〜3、新規エラー 0、76〜88 分 (2 回) |
| v6 | 上限を時間 (900 秒) から回数 (20 パス) に | 未接続 0、新規エラー 0、3 分 | **未接続 0、新規エラー 0**、124 分 |
| v8 | 上限 100 パス、最適化に渡す DSN の修正 | — | **未接続 0、新規エラー 0**、129 分、最適化も採用 |
| v11 | くり抜きの判定の修正 (01c6432)、上限 100 パス | 未接続 0、新規エラー 0、11 分 (最適化は悪化したので不採用) | 影響なし (くり抜きは本物の穴 4 個だけ) |

1. やり直しの回は、前回の配線を引き剥がせる形 → 未接続の周り 3 mm だけ引き剥がせる形 → 全部固定、の順に試す
   (`resume_ripup`、`local_ripup_mm`)。残りが多いうちは全体の引き剥がしが効き (OpenDrone で 2 回目に 76 → 3〜5 件)、
   残りが数件になると逆効果になる (3 → 10〜22 件)
2. やり直しの回は 8 案を並列に回す。乱数シード違いではなくコスト違い (ビアを安く、層の向きに逆らう線を高く、
   引き剥がしやすく)。OpenDrone では `nofan_cheapvia` (ファンアウトなし + ビアを安く) が最良だった
3. 最適化段は完走してから 1 回だけ走らせる (`optimize`)。未配線が残っているうちに走らせても改善しない
4. 部品・パッドに個別に設定したクリアランス (OpenDrone の U6 は 0.2 mm) を DSN に書き込む。KiCad の DSN 出力は
   これを落とすので、以前のクリアランスエラーはすべて U6 の周りだった
5. ベタ専用層 (power 層) のベタ定義は、つながらなかったときも DSN から外さない。外すと Freerouting はその層を
   信号層として扱い、信号を引く (以前の OpenDrone の「未接続 0〜3」は In1.Cu に信号線 200 本前後を引いた結果で、
   v4 より前の OpenDrone の数字はこの点で比べられない)

### 外形のくり抜きの誤判定の修正 (2026-11-18、01c6432)

以前は、外形線の図形ごとに「外接矩形が基板全体の外接矩形に接していないもの」を基板内側のくり抜きとみなし、
周りを両面で配線禁止にしていた。曲線や凹みのある外形の辺、1 枚に並べた複数基板の内側の辺までこれに当たる。
くり抜きは KiCad の外形ポリゴンの穴だけから作るよう直した (01c6432)。さらに、穴の外接矩形ではなく穴の形そのもの
(基板端クリアランスぶん広げた多角形) を禁止にした (dce4603)。凹んだ穴の外接矩形は基板の広い範囲を覆うため。

| 基板 | 誤った配線禁止 | 修正前 | 修正後 |
|---|---|---|---|
| Ferris 0.1 (分割キーボード、2 層、左右 2 枚を 1 つに並べた外形、424 パッド) | 44 か所 (左基板下辺の円弧から 71 x 10 mm など) | 未接続 14 (U1 の周り)、新規エラー 0、2 時間 05 分 | **未接続 0、新規エラー 0**、4 分、最適化も採用 |
| StickHub | 14 か所 (いずれも 0.4 mm² 以下の図形から) | 未接続 0 | 未接続 0 (差は出なかった) |
| Lily58 Lite Rev3 (kata0510/Lily58、2 層、218x160 mm) | 01c6432 では穴 5 個の外接矩形 (穴の面積の計 5929 mm² に対し 16563 mm²) | 01c6432: 1 回目が 3600 秒で時間切れ、未接続 64 (メモリ 7.9 GB の Linux マシン) | dce4603: 未接続 0、穴クリアランスのエラー 21。NPTH の修正後: **未接続 0、新規エラー 0**、9 分 |

Ferris は KiCad 5 形式の基板 (pierrechevalier83/ferris の 0.1/base) を KiCad 9 で保存し直したもの。
ロゴの部品 3 個が参照名 `G***` で重複していて KiCad の DSN 出力が失敗したので、DSN と SES の間だけ別名にする処理も足した (04122cb)。
ほかのベンチ基板 (作者の 4 層基板、pic_programmer、multichannel_mixer、OpenDrone) は、修正の前後で配線禁止が変わらない。

### OpenDeck v2.2.1 メイン基板 (2026-11-20)

shanteacontrols/OpenDeck の sch/opendeck/v2.2.1 (2 層、832 パッド)、既定の条件。

| 版 | 結果 |
|---|---|
| 上限 300 秒、くり抜きの修正前 (メモリ 7.9 GB の Linux マシン) | 未接続 24 |
| cb79808 | 未接続 8 (すべて USB-C コネクタ J3)、熱逃げのエラー 36、4 時間 34 分 |
| パッドの上のレジスト開口の修正後 | **未接続 0**、熱逃げのエラー 20、37 分 (2 回目で完走) |

J3 (USB-C) のパッドは自身にレジスト開口の層 (F.Mask) を持たず、パッドの上に F.Mask の多角形を図形として描いている。
frplus はこれをロゴなどと同じ「パッド以外のレジスト開口」とみなしてパッドの上を配線禁止にしていたので、
Freerouting は J3 のパッドに線をつなげなかった。1 つのパッド (0.1 mm 広げた範囲) にほぼ収まる開口は禁止にしないよう直した。
はんだジャンパのように 2 つのパッドの隙間にまたがる開口 (StickHub の JP1) は禁止のまま残る。

残る熱逃げのエラー 20 件は、GND ベタにつながるパッドの熱逃げが他ネットの線でふさがれたもの。`thermal_retry` で
4 案をやり直しても 26〜39 件で、減らなかった。この基板では熱逃げにかかわるパッドが多い。許容するなら `accept_errors` に入れる。

### 熱逃げのエラー (2026-11-19)

Freerouting はベタの熱逃げのスポークを考えずに、ベタにつながるパッドのすぐ脇へ他ネットの線を通す。スポークの先にベタが入れなくなるか、
入っても周りの線に囲まれて島になり、KiCad の DRC で `starved_thermal` になる。Lily58 Lite Rev3 では、案を 1 つだけで回すと
J9 (TRRS ジャック) のシールド端子で 5 回中 2 回出た。どこに線を通すかは案や実行ごとに変わり、複数の案を回すと出ない案が選ばれる。
そこで、完走して残ったのがこのエラーだけのときは、最良の結果を作った回と同じ入力 (最適化の前) を別の案で配線し直し、
良くなればそれを最適化する (`thermal_retry`)。最初の版 (d43d996) は最適化の入力 (配線が載ったもの) から最適化つきでやり直していて、
線をほとんど作り直せず、メモリ 7.9 GB の Linux マシンの Lily58 では 3 案とも未接続 1 になったうえ 1 本 10 分前後かかった。直した版では、エラーが出た回で
`noneck` の案が未接続 0・エラー 0 になり、最適化の後もそのまま採用された。

同じ回で、4 案を同時に動かしたメモリ 7.9 GB の Linux マシンでは 1 本が例外も残さず止まっていた。同時に動かす本数は
搭載メモリに合わせて抑える (`max_parallel`)。

試して採用しなかったこと: スポークの通り道を他ネットの配線禁止にする方法。スポークの数の判定は合っていた (配線前からある 2 件を言い当てた) が、
確保したスポークの先のベタが周りの線で島になり、エラーは消えなかった (通り道を 1 mm 延ばしても同じ)。
OpenDeck (熱逃げのエラー 20 件が残る基板) でも、熱逃げにかかわるパッド 188 個すべてについて通り道 373 か所を禁止にして試した
(2026-11-20)。熱逃げのエラーは 0 になったが、配線できる場所が減って、4 時間 29 分かけても未接続 4 件と穴どうしの間隔のエラー 1 件が残った
(禁止しない版は 37 分で未接続 0)。熱逃げのエラーを残してでも完走させるほうを選び、採用しなかった。
このときのエラーは、ピンヘッダの GND ピンのまわりの B.Cu を他ネットの線が上下左右からふさいだもので、元の手配線は
そこ (ピンから 2 mm 以内の B.Cu) に線を 1 本も通していなかった。

### 試して採用しなかったこと: 通らなかったネットを先に引かせる

やり直しの回で、前の回に通らなかったネットを専用のネットクラスに移し、開発版の `priority_net_classes` で
毎パス先に引かせる案を 2 つ足した (2026-11-16)。OpenDrone では 2 回目に 29 件で 8 案中の最下位
(`nofan_cheapvia` に足した版も 14 件)、StickHub では差が出なかったので外した。この実行は全体でも未接続 10 件と
v4 (3 件) より悪く、優先指定と関係の無い `default` も 5 → 18 件とばらついた。開発版の結果のばらつきは大きく、
OpenDrone の「未接続 3」は良いほうに振れた結果の可能性がある。

### 試して採用しなかったこと: 同じ基板を領域に分けて並列に配線する

Freerouting の配線本体は 1 スレッドなので、基板を 2 つに分けて同時に配線し、最後に全体で仕上げる方法を
`tests/partition_trial.py` で試した (OpenDrone、上下に分割、片側だけのネット 75 本と 74 本、またぐネット 45 本)。

| | 1 パス目 | 終わるまで | 未配線 |
|---|---|---|---|
| 分割なし (全ネット) | 247 秒 | 905 秒 (時間切れ) | 68 |
| 上半分だけ / 下半分だけ | 6 秒 / 7 秒 | 740 秒 / 903 秒 | 30 / 33 (片側だけのネットで) |
| 分割の結果から全体を配線 | 208 秒 | 904 秒 (時間切れ) | 96 |

1 パス目は 30 倍以上速くなるが、時間の大半は通せない接続への再挑戦で、領域を狭めても減らない。
反対側を迂回に使えないぶん質も落ち、その結果から全体を配線すると、何も無い状態から始めるより悪くなった。

v6 の OpenDrone は、1 回目の 20 パスで未接続 43 件 (900 秒で打ち切っていた頃は 68 件)、2 回目に 2 件、3 回目の
「未接続の周りだけ引き剥がす」で 0 件になった。最後の最適化は未接続 8 件に悪化して捨てられたが、これは
最適化に渡す DSN の不具合 (4a6b6c2 で修正) によるもの。StickHub は 1 回あたりが短くなり、どの回も
20 パスに届く前に Freerouting 自身が止まった。

v8 の OpenDrone は 2 回目で完走した (1 回目は 4 案の最良が未接続 36 件、20 パスのときは 43 件)。ただし 1 回目の
4 案中 2 案、2 回目の 8 案中 2 案が保険の時間上限 (3600 秒) で打ち切られており、この規模の基板では
結果がまだマシンの速さに少し左右される。打ち切ったときは結果に注意を表示する。

### 人手で一部を引いてから自動配線した場合 (2026-11-16、`tests/make_partial.py`)

元の手配線のうち、電源と USB のネットと、24 ピン以上の部品のファンアウト (パッドに端がある線と 1 mm 以内のビア) を
ロックして残し、残りを自動配線した。

| 基板 | 結果 |
|---|---|
| StickHub | 未接続 6 (すべて USB ハブの差動ペア)、31 分 |
| OpenDrone | 未接続 16、ショート 11、クリアランス 3、3.7 時間 |
| OpenDrone (内層のパッド形状の修正後、v9) | 未接続 11、**新規エラー 0**、4.4 時間 |
| 同上、案内された 8 ネットを `release_nets` に入れて再実行 (v9r) | 未接続 20、新規エラー 0、4.5 時間 |
| StickHub (くり抜きの判定の修正後、上限 100 パス、v11) | 未接続 6 (すべて USB ハブの差動ペア)、新規エラー 0、43 分 |

どちらも配線なしより悪い。ファンアウトだけ引いて先を自動配線に任せると、ロックした短い線の先端につなぐ形になり、
そこで詰まる (未接続はほぼすべてこの形)。結果にこのネットを示して `release_nets` を案内するようにした。ただし OpenDrone では、案内に従って 8 ネットのロックを外しても
未接続は 11 → 20 件と減らなかった (外した 8 ネットのうち 4 ネットはまだつながらず、混み合った場所の
別のネットが代わりに切れた。2 回目の時点で 13 件と 22 件で、実行ごとのばらつきも大きい)。
密集した場所では、ロックを外すだけでは片付かない。
OpenDrone のショートは、スルーホールのパッドの内層の形が DSN に無かったため。最初の修正 (fdf16ed) は
内層に穴径の円を足したが、KiCad ではこのパッドは内層にも表と同じ 0.9x1.4 mm の銅を持つので小さすぎ、
v8 でもショートが 20 件残った。表の層と同じ形を内層に写すよう直した。

OpenDrone の元の配線自体にもクリアランスエラーが 12 件ある。配線は毎回 `timeout_sec` (900 秒) で打ち切られている。
開発版は同じ入力でも結果が実行ごとにばらつく。同じ設定の OpenDrone を 2 回回すと未接続 3 と 1 で、
2 回目の `default` 単独では 5〜18 件の幅があった。1 回の比較の差は過信しないこと。

開発版は最適化段が走るので仕上がりも良い (90 度の折れが 2〜7 割減、パッド手前の線幅の絞り込みがほぼ無い)。乱数シード違いの案 (`seed1` など) は開発版でだけ使えるが、効果は誤差の範囲だった。
